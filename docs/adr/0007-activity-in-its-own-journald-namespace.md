# Activity lives in its own journald namespace, recorded by the CLI's dispatcher

ADR 0004 put Activity into journald instead of an own log format (the spec still mentions an append-only JSON-lines record; this replaces it). Activity needs a retention of its own (90 days by default, configurable) that neither deletes the Host's other logs nor lets them push Activity out through journald's size limits. We record Activity as structured journal entries (identifier `agentbox-activity`, fields `AGENTBOX_KIND`, `_ACTION`, `_VM`, `_ACTOR`, `_OUTCOME`, `_DESCRIPTION`) in a journald namespace `agentbox`, and run the proxy and the GitHub token service in that namespace too (`LogNamespace=`), so Alerts and GitHub tokens share the same retention. `agentbox regenerate` writes `/etc/systemd/journald@agentbox.conf` with `MaxRetentionSec` from the settings and `MaxFileSec=1day`, so journald deletes entries within a day after they expire; `agentbox activity` never shows older entries in any case.

The CLI's dispatcher records every command except an explicit list of read-only ones, so a new command is recorded without anyone remembering to; the actor comes from a global option `--actor` that the Control Room and timers pass. Entries are written with journald's native protocol from the standard library.

_Amended by #85 (2026-11-08):_ `vm/setup-vms.sh` is gone. The RPM ([ADR 0009](0009-agent-box-ships-as-a-fedora-rpm.md)) creates the group and brings the drop-in; `agentbox setup` makes the members match those of `libvirt` on every run and gives sockets created before the drop-in applied their group and mode in place.

## Consequences

- The proxy's and token service's logs are read with `journalctl --namespace=agentbox` (or `+agentbox`, which adds the default journal, where they were logged before the move).
- Entries recorded under `agentbox-activity` count only from the namespace. Entries that reached the default journal (before the namespace existed, or from tests) are not part of Activity.
- Retention is one number for all of Activity. Proxy logs are kept as long as Activity, which is what evidence of a VM's network traffic needs.
- Who may write into the namespace is decided when writing, never when reading, so an entry that was allowed when it was written stays in the history whatever happens to group memberships later. The namespace's sockets belong to root and the group `agentbox-journal`, mode 0660 (a drop-in for `systemd-journald@agentbox.socket` from `vm/setup-vms.sh`). Its members are those of `libvirt`, who manage every VM and are Host admins in effect, so the trust boundary of Activity is the access to the VMs; `setup-vms.sh` makes the members match on every run. The Control Room has the group as a supplementary group. The proxies and token services have it as their primary group: systemd connects a service's stdout and stderr with its user and primary group before it adds supplementary groups, and sends them to `/dev/null` if that fails. Anyone else's command runs and says that it was not recorded.
- Each writer may write only its own kinds of entries, so that a compromised service, above all a proxy, cannot fake others. Readers check the fields journald adds itself (`_UID` from the kernel, `_SYSTEMD_UNIT` from the sender's cgroup). Under `agentbox-activity`, the CLI's commands and events count from any `_UID` and without a unit, because journald misses the unit of a CLI that has already ended; sign-ins and sign-outs only from `agentbox-web.service` as `agentbox-web`, without a VM; nothing from the proxy and token service users, and no Alerts or GitHub tokens. `agentbox-proxy-<vm>` and `agentbox-gh-<vm>` count only from that VM's proxy or token service unit, running as its user. Their logs are also read from the default journal, which anyone can write, so readers ask `journalctl` only for entries of these users (`_UID=` matches). Readers count what they leave out, and `agentbox watch` does so for every entry under these identifiers. What remains: root and members of `agentbox-journal` can forge command entries, a service can forge lines for its own VM (and slow down every read by flooding entries it may not write), and any writer can flood the namespace so journald deletes old entries early. The services are known by the uids of their users, which the setup scripts create once; a user created again with another uid would hide its earlier lines.

## Considered Options

- `MaxRetentionSec` in a drop-in for the system journal: rejected. It would delete all of the Host's logs after 90 days, and a noisy Host could still push Activity out early through the size limits.
- Filtering by age only when reading: rejected, nothing would be deleted, so it is no retention.
- An own JSON-lines file: rejected by ADR 0004; appending safely from several processes, pruning and reading back would all be ours.
- `systemd-cat` or `logger` to write: rejected. Structured fields need the native protocol, which takes a few lines of standard library and no extra process.
- Recording in each command handler: rejected, commands added later would be missed.
- Matching every trusted field in `journalctl` (`_SYSTEMD_UNIT=…` too) instead of checking the unit when reading: rejected. A token service unit is named per connection, `agentbox watch` follows the whole namespace, and entries of the services' own users that `journalctl` left out could not be counted.
- Checking only when reading, with world-writable sockets: rejected. Any local user could write entries and slow down every read, and the reader would have to decide who may write. Checking group membership when reading would also make entries disappear from the history when someone leaves the group.
- The group only in `SupplementaryGroups=` of every service: rejected. systemd connects the log stream before it adds them, so the proxies' and token services' logs would go to `/dev/null`.
