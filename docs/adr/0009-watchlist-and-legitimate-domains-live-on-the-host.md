# The Watchlist and the Legitimate domains live on the Host; changes that lift strong Signals need --force

The hand-maintained Watchlist and the Legitimate domains were files in the repository (`proxy/suspicious-domains`, `proxy/legitimate-domains`) that `vm/setup-vms.sh` copied over the Host's copies on every run. Adding one domain took a pull request and a run of `setup-vms.sh`, while the Allowlist and the Harmless marks were already edited from the CLI and the Control Room. Both lists now are records on the Host, like the Allowlist: `/etc/agentbox/watchlist.json` and `/etc/agentbox/legitimate.json`, root-owned, written only by `agentbox` (`watch-add`, `watch-remove`, `watch-set-note`, `legitimate-add`, `legitimate-remove`, `legitimate-set-note`), with who added an entry and when, and every change recorded in Activity. The classifier reads them directly and re-reads them when they change. `agentbox migrate-lists` takes the Host's text files over once. The repository's files only fill a new Host: `setup-vms.sh` installs them only where there is no record, no text file and no `*.migrated` file.

Editing these lists can weaken a safeguard. Open web keeps destinations with strong Signals blocked, and the Control Room can never allow such a destination (it never passes `--force`). Removing a Watchlist entry of a strong category, lowering one to a weak category, or adding a Legitimate domain that would lift strong Signals would make such a destination reachable in Open web. Strong Signals here are the domain's own (a Feed entry above it included), or entries of the threat-intelligence Feed at or below it, also those a Legitimate domain of the Host lifts now: that one can be removed again, and the new domain would keep them lifted (`c2.vendor.example` added below `vendor.example`, then `vendor.example` removed). The check sees them because `agentbox-feeds` stores the Feeds as fetched and Legitimate domains lift Feed hits only when the classifier classifies. One case cannot be checked, so it needs `--force` as well: any new Legitimate domain while there is no threat-intelligence list (before its first fetch). Below a built-in Legitimate domain nothing can come back, so no `--force` is needed there. All these changes therefore need `--force`, and only the CLI on the Host can do them. Adding Watchlist entries, removing Legitimate domains and editing notes work from the Control Room.

_Amended by #23 (2026-11-12):_ `github.io` and `githubusercontent.com` keep the pattern Signals off the brand, but Feed hits on their subdomains count. No Legitimate entry lifts those Feed hits, also not one of the Host below one (however specific), so below a built-in domain nothing can come back, as before: `legitimate-add` needs no `--force` there.

A Legitimate domain does not lift the blockchain pattern (labels such as `rpc.`, `mainnet`, `solana.`, names such as `infura`): it stays a strong Signal below every Legitimate domain, of the Host or built in. A Legitimate domain is a whole site, and a blockchain endpoint below it (`mainnet.base.org` below `base.org`) is exactly what the pattern is for, so `legitimate-add` cannot make one reachable in Open web; only `allow --force` on the CLI can.

A Watchlist that cannot be read closes Open web. When `watchlist.json` is broken, or missing without the text file from before, the proxy does not know which destinations Open web must keep blocked, so Open web lets nothing through (`BLOCKED <host> (Watchlist unreadable, Open web closed)`); Allowlist entries still work, so agents keep working. This holds whether or not the proxy still has an older state in memory: a proxy started later has none, and every proxy should decide the same. A single broken entry (an unknown category, a duplicate domain, a missing field) makes the whole record broken, for the proxy as for `agentbox`: a typo in the category of a strong entry would otherwise make it weak. Alerts keep using the last good state. Allowlist entries pass the proxy while Open web is closed, so `allow`, `extend` and `make-permanent` need `--force` for every destination then (the classifier exits 3); otherwise the Control Room could allow `webhook.site` while the Watchlist is gone. The Watchlist commands and `open-web` refuse with the reason until the file is fixed; `agentbox watchlist` and the Control Room show it in place of the entries, next to the Feeds' state. Only `watch-add --force` creates a missing record again: that opens Open web again, so the Control Room, which never passes `--force`, cannot; on the CLI it is the admin's repair path. `migrate-lists` creates no Watchlist where there is neither the record nor the text file: an empty one would open Open web with nothing on it. A broken record of the Legitimate domains, also in a single entry, keeps its last good state in the proxy (without one, only the built-in domains count): it can only add Signals, so it fails safe. The self-test fails on it, `agentbox` refuses the Legitimate-domain commands with the reason (`legitimate_unreadable` in the Control Room), and `migrate-lists` with nothing to migrate only warns, so `setup-vms.sh` goes on.

_Amended by #85 (2026-11-08):_ `vm/setup-vms.sh` is gone. The RPM ([ADR 0009](0009-agent-box-ships-as-a-fedora-rpm.md)) ships the repository's lists in `/usr/share/agentbox/lists`, and `agentbox setup` does what the script did here: it installs them only where there is no record, no text file and no `*.migrated` file, goes on when `migrate-lists` only warns, and does not refill a deleted record but says how to restore it.

## Consequences

- The migration never weakens an entry. A domain listed twice in the text file keeps its strongest category. Lines the records cannot take (an unknown category such as `threat`, which the classifier read as strong, or an invalid name) are left out only by `migrate-lists` on the Host, which names them and records how many in Activity; a change that would migrate such a file refuses (`migration_required`), so the Control Room cannot drop them unseen.
- Changes to the repository's lists no longer reach existing Hosts. A Watchlist entry from a new incident is added on each Host with `agentbox watch-add`.
- The built-in Legitimate domains (the classifier's `GENUINE` set: registries and vendors) stay in code. They cannot be removed, and the migration does not copy them into the record.
- The detection self-test runs against the Host's lists plus its own fixtures (for each list its record, before the migration its text file, on a fresh Host the repository's), so a broken record fails it, and it checks one real Watchlist entry of the Host if there is one. Its cases use names under `.example`, except the built-in Legitimate domains it checks; where a Host entry covers one of these, its category is expected as well, so ordinary entries never fail the self-test. It no longer needs any particular entry such as `webhook.site`, so every hand-maintained entry can be removed.
- `agentbox-feeds` stores the Feeds as fetched; Legitimate domains lift Feed hits for themselves and below only when the classifier classifies (a label walk against a set, a few microseconds per destination). Removing a Legitimate domain therefore brings its Feed entries back at once, and a Feed entry above a Legitimate domain (`vendor.example` above `cdn.vendor.example`) still counts for its other subdomains. The Feeds' entry counts include the entries Legitimate domains lift; how many those are is not shown, because counting them means reading the whole lists.
- A hand edit that breaks `watchlist.json`, or deleting it, closes Open web for every VM until the file is fixed; repairing it opens Open web again without a restart. `setup-vms.sh` does not refill a deleted record from the repository, whose list would be stale; it says how to restore it.
- `legitimate-add` reads the whole threat-intelligence list (about 40 MB through the page cache) to find entries at or below the domain; this is acceptable for a rare command.

## Considered Options

- Keep the lists in the repository: rejected. A pull request and a Host-wide setup run for one domain is too slow when an Alert is a false positive or an incident is unfolding.
- Repository lists plus a Host overlay: rejected. Two sources and the rules for merging them would be harder to explain than one record.
- Let the Control Room lift strong Signals: rejected. A stolen Control Room session could then remove `webhook.site` from the Watchlist, open the web and send data out, which the existing `--force` rule for `allow` is meant to prevent.
- Keep the last good state of a broken Watchlist for Open web, as for the Allowlist: rejected. A proxy started after the file broke has no such state and would run Open web without the hand-maintained Watchlist, and proxies started at different times would decide differently.
- Built-in Watchlist entries for the self-test: rejected. The self-test brings its own fixtures, so nothing in the Watchlist has to be pinned in code.
