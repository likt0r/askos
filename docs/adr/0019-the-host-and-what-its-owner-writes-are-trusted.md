# The Host, its admins and what its owner writes into Images are trusted

The threat model named two threats, rogue agents and supply-chain attacks, and three things out of scope: theft of the Host, targeted attacks against its owner, the laptops. It did not say whom Agent Box trusts. So each review had to guess how hostile an Image may be: the review of #127 went five rounds finding ways a file crafted for the purpose reads otherwise for sshd or systemd than for the Safeguard check, and each fix asked for the next. The owner sharpened what Agent Box is for and whom it trusts (2026-11-18).

## Decision

- **What Agent Box is for.** It shrinks the blast radius of coding agents: work and private kept apart in different VMs, least privilege for agents, protection against rogue or manipulated agents and supply-chain attacks in the daily work in a VM (the package minimum age, the VM bounding what malicious code reaches, detection of known malware and exfiltration destinations at the proxy), and little worth in a credential leaked by accident. ARCHITECTURE's threat model lists these five. Building an Image is not daily work: there only the package minimum age and the pins stand against a malicious package, which runs as root on the Host (the owner, 2026-11-18).
- **The Host and whoever administers it are trusted**: root, the members of `libvirt` and the owner signed in to the Control Room. They control every VM anyway; nothing in Agent Box defends a VM or a credential against them.
- **Someone who only gets hold of such access is not trusted.** A stolen Control Room session, a process on the Host guessing the password: what stands against them is the Control Room's sign-in and, until the Control Room uploads Recipes (#119), the limits of what it offers (strong Signals lifted only on the CLI with `--force`, [ADR 0009](0009-watchlist-and-legitimate-domains-live-on-the-host.md)). Once it uploads Recipes, a Recipe written through a stolen session reaches root on the Host through the disk step, and the sign-in alone stands against it; the Safeguard check never does.
- **What goes into an Image by the owner's hand is trusted.** The Release's Containerfiles (reviewed code on `main`, installed by the owner with the Release, [ADR 0010](0010-images-are-built-from-the-installed-release.md)) and the owner's Recipes ([ADR 0018](0018-recipes-define-images-on-the-host.md)) are written, or reviewed, in good faith. The Safeguard check after every Build ([ADR 0008](0008-safeguards-checked-from-the-host-after-every-build.md)) catches mistakes and convenient edits in them that weaken a Safeguard; an Image its author made to get past it is outside the threat model. Code that runs during a Build is not trusted: a package or a download there is a supply-chain attack and can undermine a Safeguard in a way the check does not look for. What a Build installs through npm or uv has a minimum age, and so has Orca; pnpm and Bun have theirs only in the VM, Fedora's packages none, and other downloads only what a Containerfile pins, and a Build reaches the internet without an Allowlist. A Recipe an agent wrote and nobody reviewed is a rogue agent's work.
- **Code in a VM is never trusted**, at any time: what it can write at runtime (its home, `/tmp`, `/run/user`) must never decide what root in the VM or on the Host does.

## Consequences

- The Safeguard check stays as it is and reads the Image's files from the Host ([ADR 0008](0008-safeguards-checked-from-the-host-after-every-build.md)). A new check is written against mistakes and against what code in a VM can change at runtime; reviews take an Image crafted to get past a Safeguard as out of scope. Reading the Image safely is not: code that runs during a Build can craft any file, so the check, as root on the Host, follows links only inside the Image, reads regular files only and parses no more than a bounded size of each, whatever the Image holds. The disk step that follows runs the Image's own `bootc` privileged on the Host, so code planted in a Build reaches root on the Host there; ARCHITECTURE lists that among the limits. The sshd check of #127 is cut back to that.
- ADR 0008 and ADR 0018 are amended: the check does not bound what a stolen Control Room session builds, the sign-in does.
- Checks against the Host's own input into a VM (the keys of SSH access, #126) are plausibility checks, not a boundary.
- "What it does not protect against" keeps saying how far the trusted admins reach, so the owner knows what they hold. That an Image's author could undermine a Safeguard on purpose is no longer a limit there; that a package can during a Build still is.
- The Claude token per VM is long-lived. Against a credential leaked by accident it is the weak point; ARCHITECTURE lists it under Credentials in a VM.

_Amended by #144 (2026-11-23):_ the disk step no longer runs the Image's own `bootc`. bootc-image-builder, pinned by digest, takes the pristine `fedora-bootc` the Image is built on, also pinned by digest, as osbuild's buildroot (`--build-container`), so the `bootc` that runs `bootc install to-filesystem`, osbuild's Python and the tools that make partitions and filesystems come from that image, not from the Image. Image code still runs there in two places. bootc, by design, runs the Image's own `bootupctl` chroot'ed into the installed Image, as root in the privileged builder, and with it `grub2-install`. A tool a Build planted there reaches root on the Host without any escape. Before that, bootc-image-builder runs `bootc install print-configuration`, `bootc container inspect` and `lsinitrd` of the Image in an unprivileged container of its own, as podman runs a Build's `RUN` lines. ARCHITECTURE lists both under Agent Box's own code, and says why bootc-image-builder's own image cannot be the buildroot (Images and Builds). The consequence above holds with that narrower reach: code planted in a Build still reaches root on the Host in the disk step, through `bootupctl`.

_Amended by [ADR 0025](0025-builds-run-in-a-throwaway-build-vm.md) (#144, 2026-11-24):_ with the Setting `build_vm` on, its default, a Build's `podman build` and its disk step, the Image's `bootupctl` included, run in throwaway build VMs, and so does the version check's package count; no code from an Image runs on the Host. Code planted in a Build reaches the build VMs and the Image they make, not root on the Host; what root still runs on a Build's output are parsers (skopeo and containers/storage for the image, the Safeguard check, qemu-img for the disk's header). The consequence above, and the one of the amendment before, hold only while `build_vm` is off, which only root on the CLI can choose and which `agentbox status` and the Control Room show for as long as it lasts.

## Considered Options

- Treating every Image as possibly hostile: rejected. The check would have to read every file format a Build may hold as its program does (sshd, systemd, shells, every agent's settings), and a hostile Image can ship a changed binary no configuration check sees. Who can make Images can make them do anything.
- Trusting a Control Room session like the Host's admins: rejected. A password can be guessed or a session stolen from a browser; until the Control Room uploads Recipes it keeps what it does not offer (lifting strong Signals, `--force`) out of a stolen session's reach, and after that its sign-in is what guards the Host.
- Keeping Recipe writes to the CLI on the Host: rejected by the owner (2026-11-18). The Control Room will upload Recipes (#119), knowing that a Recipe written through a stolen session makes that session root on the Host through the disk step (ARCHITECTURE, Agent Box's own code).
- Extra confirmation (the password again) for writing a Recipe in the Control Room: not now; the Control Room's sign-in is the barrier. It can come with the one-time sign-in link (#137).
